Run it yourself: the multi-repo AI-DLC practice kit

The multi-repo runbook describes one Prior Auth feature going through AWS AI-DLC v2: urgent requests get a 72-hour clock, across three repos. This kit is how you do it, on your own machine, with Claude Code or Codex CLI.

Prefer one page? guide.html is this whole kit in a single standalone file, built from these Markdown files by build-guide.py. Re-run the script after editing a card.

There is no grading script. The point is to watch the method work:

  • the engine asking instead of guessing;
  • a reviewer agent finding gaps before you do;
  • a plan gate that stops code until a human says yes;
  • your answers in step 02 turning up, three stages later, in requirements and code.

What you'll learn

By the end you will have:

  • built a v2 workspace: a hub that holds the AI-DLC record, with code repos beside it;
  • run all five phases and 33 stages at enterprise scope, answering question files and passing human gates;
  • seen how steering files, the hub's memory/, and an AI-DLC plugin keep an engine inside each repo's recorded rules;
  • generated code into two brownfield repos and one greenfield repo, against a versioned contract, in two bolts;
  • copied the feature's decisions back into each repo so they outlive the feature.

The feature

The utilization management (UM) director wants urgent prior auth requests decided inside 72 hours, with nurses seeing those requests first and providers notified the moment a determination exists. An at-risk alert should fire before the clock runs out.

The deadline is not the team's invention. For Medicare Advantage, Medicaid and CHIP, and exchange plans, the CMS Interoperability and Prior Authorization rule (CMS-0057-F) sets 72 hours for expedited and 7 calendar days for standard decisions from January 1, 2026. Your compliance team owns the exact reading, including when the clock starts. In the reference run the room chose "when the request is complete", and that one answer shaped the success metrics, the requirements and the code.

Three repos have to change together, and one of them does not exist yet.

Repo What changes Starting point Unit of work
prior-auth-api (TypeScript + Jest) AuthRequest.urgency (STANDARD or URGENT) and decisionDueAt; urgent requests go to the front of the nurse review queue; emits determination.issued and sla.at-risk; publishes the contract. The auto-approve rule stays as it is: score ≥ AUTO_APPROVE_THRESHOLD (0.85). Brownfield api-urgency-clock
prior-auth-web (React + Vitest) Urgency badge and countdown in AuthQueue; URGENT first, then by due time. Brownfield web-urgent-queue
prior-auth-notify (new, TypeScript) Consumes the two events; sends provider and member notices with status and referenceId only (decision D-003: no clinical content). Greenfield notify-service

Where Markdown lives

The most common multi-repo mistake is putting the feature record inside one of the service repos. The other repos can't see it, and it outlives the feature in the wrong place. AI-DLC v2 avoids this with a workspace: a hub folder that holds the AI-DLC record, with each code repo cloned beside it. Markdown ends up in three homes, and each has one rule.

Home Path The one rule What lives there
1. The hub prior-auth-workspace\aidlc\ Everything about the feature. The hub is its own git repo. The intent record (state, audit, every stage's artifacts); per-repo code knowledge in codekb\<repo>\; the team method in memory\ and standards in knowledge\
2. Each code repo prior-auth-workspace\prior-auth-*\ Everything that must outlive the feature. Code and tests (generated into the repo, never the hub); steering in AGENTS.md, which CLAUDE.md imports; docs\decisions.md, the durable domain decisions, copied over from the hub's ADR log at close-out
3. The tracker prior-auth-workspace\tracking\rally\ → Rally A mirror for reporting, never the source of truth. An import file the AI drafts and a human imports; one map file of Rally IDs; state moves at human gates, not on AI activity

The hub's .gitignore lists the three sibling folders, so the hub never commits application code. Each sibling keeps its own .git and its own history. AWS ships no Rally or Jira integration; home 3 is this course's convention.

Step 01

Build the hub workspace and its three sibling repos

Background

AI-DLC v2 runs a multi-repo feature from a workspace: a hub folder that is its own git repo and holds the AI-DLC record, with each code repo cloned beside it as an immediate child. Each child keeps its own .git. When you describe the work in step 02, the engine scans the hub, finds the siblings on disk and records them in the intent's registry row. You never pass a repo list by hand.

The layout is the lesson, which is why you build it yourself instead of running a script. Where a file sits decides three things:

Question Answered by
Who can see it? A file in the hub is visible to every unit; a file in prior-auth-api is visible only when the engine works in that repo.
What gets committed where? The hub's .gitignore lists the three siblings, so the hub commits the record and never the code. Each repo commits its own code.
What outlives the feature? The intent record is about this feature. A repo's AGENTS.md and docs\decisions.md are about the repo, and stay with it.

The pieces

  • repos.json at the hub root declares the expected siblings. aidlc system workspace-sync clones any that are missing, rewrites a managed block in .gitignore, and writes aidlc.code-workspace, a multi-root VS Code file. A teammate can rebuild the whole workspace from it with one command. Give each entry a url: without one, AI-DLC clones git@github.com:<org>/<name>.git over SSH. The kit's copy points at local folders, so the exercise runs offline.
  • aidlc config --harness <engine> installs the engine side: agents, stage rules, scopes, sensors, hooks and the onboarding file. For Claude Code that is all under .claude\; for Codex, under .codex\ and .agents\. The hooks are what make the method binding rather than advisory: one records each human turn into the audit trail, one guards tool calls against the current stage, one blocks code until a plan is approved, and a Stop hook keeps the workflow moving.
  • aidlc\spaces\default\memory\ holds the team's method: org.md, team.md, project.md and one file per phase. Every stage of every intent loads it.
  • aidlc doctor checks the machine, the project and the framework files.

The steering-file question

You start the engine at the hub. Each repo's rules live in that repo's AGENTS.md and docs\decisions.md: for example, prior-auth-api D-001 (a criteria score ≥ 0.85 auto-approves) and D-003 (notices carry status and referenceId only). Nothing guarantees an engine running from the hub reads a nested repo's steering file before it edits that repo. So you say it once, in the method file every stage loads: memory\project.md.

The kit's seed\memory-project-steering.md holds three blocks for the headings already in that file. Way of Working says to read each repo's rules first and that one unit of work is one repo. Forbidden says never change a recorded rule, never put clinical content in a payload, never import code across repos. Mandated says to cite the D-id in any plan step that touches a recorded rule. Step 02 is where you see the engine quote them back. This pointer is a course convention built on AWS's documented memory files.

Greenfield next to brownfield

prior-auth-api and prior-auth-web are brownfield: real code, real tests, recorded decisions. prior-auth-notify starts with steering files, a decision log and an empty src\. It is greenfield; the engine writes its code in step 08. Its seed decision log already records D-001, which restates prior-auth-api's D-003 for the repo that will send the notices.

Runbook section: 01 · Workspace setup · Phase: before the lifecycle · Time: 30–40 minutes, once

Goal

Build, by hand, the layout AI-DLC v2 uses for a feature that spans several repos:

  • a hub folder, which is its own git repo and holds the AI-DLC record;
  • the code repos cloned beside each other inside it.

You'll do this by hand instead of running a script, because the layout is the lesson: - where each file lives decides who can see it; - it decides what gets committed where; - it decides what outlives the feature.

Who's in the room

The tech lead, alone, once per workspace. Nobody approves anything yet.

Do it

All commands are Windows PowerShell. $kit is wherever you cloned this course; change it.

1. Install the tools (once per machine).

2. Make three "remote" repos. In a real team these are on GitHub. Here they're local folders that stand in for GitHub. That way the whole exercise runs offline, and you don't need SSH keys.

$kit  = "D:\path\to\ai-dlc-course"          # <- your course clone
$root = "D:\aidlc-practice"

robocopy "$kit\prior-auth-api" "$root\remotes\prior-auth-api" /E /XD node_modules .claude
robocopy "$kit\prior-auth-web" "$root\remotes\prior-auth-web" /E /XD node_modules .claude
robocopy "$kit\runbook\practice\seed\prior-auth-notify" "$root\remotes\prior-auth-notify" /E
foreach ($r in 'prior-auth-api','prior-auth-web','prior-auth-notify') {
  git -C "$root\remotes\$r" init -b main
  git -C "$root\remotes\$r" add -A
  git -C "$root\remotes\$r" commit -m "seed: $r"
}

prior-auth-notify starts almost empty: steering files, a decision log, and an empty src/. It is the greenfield repo. The engine writes its code in step 08.

3. Create the hub and let AI-DLC clone the siblings.

mkdir "$root\prior-auth-workspace"; cd "$root\prior-auth-workspace"
git init -b main
Copy-Item "$kit\runbook\practice\seed\repos.json" .     # edit the url paths if your $root differs
aidlc system workspace-sync

repos.json declares the repo set. Each entry has a url, because without one AI-DLC clones git@github.com:<org>/<name>.git over SSH.

4. Configure the engine and check the setup.

# Claude Code
aidlc config --harness claude --yes
aidlc doctor

# Codex CLI: the same hub can hold both engines
aidlc config --harness codex --yes
aidlc doctor
codex          # first run only: type /hooks, press t to trust all, then Esc

5. Install each repo's dependencies.

foreach ($r in 'prior-auth-api','prior-auth-web','prior-auth-notify') {
  Push-Location $r; npm install; npm test; Pop-Location
}

6. Teach the hub to respect each repo's rules. Open aidlc\spaces\default\memory\project.md. Paste each block from $kit\runbook\practice\seed\memory-project-steering.md under the heading of the same name: Way of Working, Forbidden, Mandated. Then commit the hub:

git add -A; git commit -m "hub: repos.json, aidlc config, repo steering"

7. (Recommended) Install the learning helpers. Follow extensions/README.md. It takes about 10 minutes and gives you: - aidlc-coach, which explains where you are; - repo-plan-reviewer; - the decision-log guard; - the prior-auth-pack plugin.

Scope: say it out loud

Scope decides which of the 33 stages run and how deep each goes. With no --scope, AI-DLC v2.11 uses classic, which skips Ideation and Operation. This feature needs both.

Scope Stages Fit for this feature
enterprise 33, comprehensive depth, strict guard policy Chosen: PHI, a regulatory deadline, three deployables, and Operation stages you'll need (SLO, alarms, rollback)
feature 33, standard depth Fine if compliance doesn't need comprehensive artifacts; a faster first pass
classic 18, v1-style; no Ideation, no Operation Loses the deploy and observe stages the deadline depends on

Choosing the scope is a team decision. You can change it mid-run with /aidlc --scope <name>.

The stage rhythm

Every Ideation stage, and nearly every stage after it, goes the same way:

  1. Questions in a file. The engine writes <stage>-questions.md with multiple-choice questions, each ending in an [Answer]: tag, and a Sources list at the top citing your description and your memory\ rules. You choose how to answer: guide me (in chat), I'll edit the file, or chat and let the engine extract decisions.
  2. Follow-ups. If an answer opens a new question, or collides with a recorded rule, the engine adds Q12, Q13 and so on. That is the method working, not a loop.
  3. Summary confirmation. Before writing anything, it restates every answer and asks Looks correct or Request changes. Read it as carefully as the documents; it is what they are built from.
  4. Artifacts. Every statement carries a source tag: [Q4], [desc], [memory:M2].
  5. AI review. At enterprise scope a reviewer agent (here, a product lead) raises numbered findings, and the engine gives its own view of each.
  6. The gate. Approve, or Request Changes: <what and why>. New facts you give at the gate become new numbered answers, so the revised documents can cite them.

The decisions do not live in chat. The question file holds the answers, and audit\<host>-<clone>.md records every human turn and every gate decision.

Step 03

Read every brownfield repo before anyone designs

Background

Ideation ended with a signed brief and a decision log. Nobody has written a requirement yet, and that is deliberate. Before the engine drafts requirements for three repos, it reads all three. AI-DLC calls this semantic context building: turning code nobody on the mob wrote this week into a short, checked description that every later stage can lean on.

2.1 Reverse Engineering is a two-step pipeline. A developer agent scans each repo and writes a scan report into the intent (inception/reverse-engineering/developer-scan-<repo>.md). An architect agent then turns each scan into nine documents in a store that belongs to the space, not the intent:

File What it answers
business-overview.md What the repo is for, who uses it, which recorded rules govern it
architecture.md How the parts fit today, with interaction diagrams
code-structure.md Where things live
api-documentation.md What the repo exposes, and what it calls
component-inventory.md Every component, with its role
technology-stack.md / dependencies.md Runtime, tooling and pinned versions
code-quality-assessment.md Findings (F-01, F-02 ...), gaps and debt
reverse-engineering-timestamp.md The commit scanned, the depth, and what was not read

Because the store lives at aidlc/spaces/default/codekb/<repo>/, the next intent that touches prior-auth-api finds it and can reuse it if the code hasn't moved. The timestamp file records the commit and a fingerprint so the engine can tell.

Each repo needs its own complete scan before approval. That includes prior-auth-notify, which is greenfield. The runbook expected nothing to scan there; AI-DLC v2.11 scanned it anyway and kept two lists apart: what the steering commits the service to, and what exists. That separation is what you check as notify lead.

What a good scan looks like. A good scan says what is not there. prior-auth-api has services and entities but no HTTP layer, no persistence and no messaging. A scan that invents endpoints would poison every stage after it, because requirements, design and code all read the codekb. The repo leads review their own repo's documents against the code, not against what they remember.

2.2 Practices Discovery settles how this team builds and tests. A release engineer agent drafts the practices from the repos' steering files. Three inspectors (quality, developer, devsecops) review the draft independently, without seeing each other's notes. The engine then asks only the questions the code can't answer: merge style, tests first or after, how the coverage floor is measured, what "checks pass" means without CI. Your answers become the team's standing rules.

Promotion is the point of 2.2. When you approve, the practices are written into memory/team.md and the ALWAYS/NEVER rules into memory/project.md. From then on every stage and every unit reads them. This is where the "read each repo's rules first" block from step 01 is confirmed, and it is the cheapest place to change a team rule: before any plan cites it.

The question file is the source of truth. Questions go into requirements-analysis-questions.md in a fixed shape: lettered options, a mandatory X. Other (please specify), and an [Answer]: tag. The ADR log records the architecture choices with their context, consequences and rejected alternatives. In a brownfield intent most ADRs come from what the existing code already does, so the steering files and decision logs you wrote in step 01 show up here. The ADR log belongs to the intent and lives in the hub. In step 10 you copy the entries that constrain a repo into that repo's own docs/decisions.md.

Units Generation cuts the work into units and tags each with a kind (service, ui, spec, and so on). The kind decides which Construction documents the unit owes: a ui unit, for example, owes no infrastructure design. This is the gate where the repo set and the unit boundaries lock. Everything in Construction is planned per unit.

Contract Design writes the agreements between units: who provides each element, who consumes it, the mechanism, the version, and the ownership rules.

Two rules make a multi-repo feature work, and both are tested at this step:

  1. One unit = one repo. During Construction the engine anchors every git operation to one repo. A unit that spans two repos fights the engine, and it also makes review and rollback unclear. If units come out uneven in size, that's honest: split a large unit into bolts in step 07, never across repos.
  2. The contract exists in two forms. contract-summary.md in the hub is the design record. The machine-readable contract (prior-auth-api/contracts/v1.1.0/) is code that the providing unit generates in Construction, and consumers pin a copy of it. Because U2 and U3 depend on the contract and not on U1's source, they can be built against it as soon as it is published.

Each of the three stages runs the same loop you met in step 02: a question file, a summary to confirm, a draft, an AI architecture review, then the gate. Two things are worth watching in this step specifically:

  • Locked documents and the ledger. Once a review is final, the documents it covered are frozen. A finding accepted at the gate is not edited in; it goes into inception/gate-decisions.md, the ledger, which every later plan must read. When you read an approved artifact, read the ledger beside it.
  • Should-fix findings accepted as risk. In the reference run, all three gates passed with should-fix findings carried forward. Each is a small debt that Construction inherits, so make sure each one names who decided it and where it will be handled.

Step 07

Background

Delivery Planning is the last Inception stage. It decides how the approved units get built: in what order, in what slices, with which human stops, and what happens when an outside decision slips. It doesn't change what the units are. The dependency graph from step 06 is fixed input.

A bolt is AI-DLC's delivery slice. In AWS AI-DLC v2 a bolt covers one or more dependency-linked units and ends in code that runs and passes its repo's gate. Bolts replace sprints: they're sized in hours to days, and each ends with a human checkpoint per unit, not a demo at a fixed date. bolt-plan.md records the grouping and the reasons for it, without touching the dependency graph.

The walking skeleton comes first. With the skeleton stance on, the first unit starts with the smallest slice that works end to end, and a human approves that slice before the rest of the unit is built. The skeleton is defined as one observable behaviour, not as a layer. Here: an urgent request goes in through the real entry point, is stored, and comes back out with its urgency. It proves the build, test and storage path is real before the hard work starts on top of it.

Order is set by dependencies and risk.

Bolt Contents Why this order
Bolt 1 U1 api-urgency-clock in prior-auth-api: skeleton, checkpoint, then the rest of U1 U1 has no dependencies and publishes the contract the others need
Bolt 2 U2 notify-service, then U3 web-urgent-queue, one unit at a time Both depend only on U1's published contract, not on each other

Inside a large unit, risk goes first: the clock edges, the concurrency, the privacy allow-lists. Delivery Planning asks what worries the room most, and each answer becomes an early, test-first item.

Construction settings are chosen here, and they matter:

  • Iteration: unit-major. Each unit runs all its design stages and Code Generation, then its checkpoint, before the next unit starts. This is the default for solo work and the one to use the first time.
  • Execution: serial. Parallel units (U2 and U3 together) need stage-major order with swarm execution. You can ask for it in plain words, but it is not the default.
  • Unit ownership. v2's team mode, where each person claims a unit in their own checkout, needs a single-repo intent. For a three-repo intent, one conductor runs Construction from the hub, and each repo lead reviews at their own unit's checkpoint. The engine refuses team ownership for this intent.
  • The verification command that every unit checkpoint will run. It can be deferred to the first checkpoint if the gate it names doesn't exist yet.

The Inception phase check closes the phase. It writes verification/phase-check-inception.md and counts things: every requirement traced to a story, every story to a component, every story to a unit. A deferral is allowed only if it names the downstream stage that picks it up. A gap fails the check. It's the boundary between deciding and building: once it passes, Construction starts writing design documents per unit, and soon after that, code.

After the gate, the Rally stories are drafted from the approved files and imported by hand. Rally is a mirror of the record, not the record.

Design, plan, then generate code into the right repo

Background

Construction is where approved decisions become code, one unit at a time. For each unit the engine runs up to five stages, each with its own folder under construction/<unit>/ in the hub:

Stage What it settles Typical outputs
3.1 Functional Design Entities, business rules, workflows for this unit entities.md, rules.md, functional-spec.md
3.2 NFR Requirements Quality targets and technology choices tech-stack-decisions.md, security-requirements.md, ...
3.3 NFR Design How the code is structured to meet them logical-components.md, reliability-design.md, ...
3.4 Infrastructure Design Where it runs. Depends on the unit's kind; a ui unit skips it infrastructure-specification.md, cicd-pipeline.md
3.5 Code Generation A plan, approved by a human, then the code code-generation-plan.md, code-summary.md, traceability.json, source-manifest.json

Four ideas carry the whole step.

The design lives in the hub; the code lives in the repo. The hub never holds application code. Code Generation writes into the owning sibling repo, on a bolt branch, and every git operation is anchored to that one repo.

No code before an approved plan. Code Generation always starts with code-generation-plan.md. AI-DLC's plan-approval-guard hook blocks edits in the unit's repo until a human approves the plan. That approval is the one switch only a human can turn. The plan carries a Repo rules honoured table (added by the kit's prior-auth-pack plugin) showing how it keeps each recorded rule, such as prior-auth-api D-001 (a 0.85 criteria match auto-approves) and D-003 (notices carry status and referenceId only). The kit's repo-plan-reviewer agent checks the plan against the repo's own steering before you answer.

Rules are enforced by tools, not by goodwill. Steering files ask the engine to leave a repo's docs/decisions.md alone; the kit's decision-log guard hook stops the edit and asks a human. AI-DLC's own guards freeze reviewed documents (review-freeze), and its sensors run type-check and lint on every .ts write. When a guard says no, the right response is to change the plan or route the change through a human, never to go around the guard.

A unit ends at a verified checkpoint. The engine runs the intent's verification command, records the proof against fingerprints of the reviewed source, and asks the owning repo's lead and the tech lead to approve. Evidence means pasted runner output, not "tests pass". Because the proof is bound to fingerprints, any change after the review makes it stale. That's what made U1 reopen in the reference run.

With unit-major iteration and checkpoints on, a unit's design stages don't each get their own gate. They are approved together at the unit checkpoint. Findings raised after a review is final go into the ledger, inception/gate-decisions.md, as rows binding on the unit's later stages, because the reviewed documents are locked.

A walking skeleton adds one more stop. The first slice of the first unit is built, verified and approved before anything is built on top of it.

Step 10

Background

Operation is where the record proves its value. The code is built and tested; this phase gets it running, decides how anyone will know it's healthy, says what on-call does when it isn't, and makes sure the feature's decisions outlive the feature.

This practice run has no cloud. "Deploy" means building and testing each repo in order, running the local smoke path, and recording that in deployment-log.md as a local run. The engine will ask about environments and infrastructure. The answer, the same one given at every Infrastructure Design stage in step 08, is "local only: document what production would need, provision nothing". The documents still matter: they are what the release owner takes to a real go-live, with HIPAA-covered hosting and privacy-office and compliance sign-off.

Operation's seven stages are conditional. Enterprise scope runs all of them, each in its own folder under operation/. The four you will read most closely:

Folder What it holds Owner

Deploy in contract order: api, then notify, then web. prior-auth-api goes first because its change is additive and backward compatible: old web and notify keep working against it. The SLO measures the requirement, not a proxy. Here it is the share of URGENT requests determined within 72 hours of becoming complete, with the sla.at-risk event as the early warning 24 hours before the deadline. Codex CLI (0.162) needs one extra step. It reads a marketplace from .agents/plugins/marketplace.json, but AWS's builder writes .codex-plugin/marketplace.json. So wrap the build output in a small marketplace folder:

$M = "D:\aidlc-practice\plugins\codex-marketplace"

$m | ConvertTo-Json -Depth 5 | Set-Content "$M\.agents\plugins\marketplace.json"

codex plugin marketplace add $M
