Run it yourself: the multi-repo AI-DLC practice kit

The multi-repo runbook describes one Prior Auth feature going through AWS AI-DLC v2: urgent requests get a 72-hour clock, across three repos. This kit is how you do it, on your own machine, with Claude Code or Codex CLI.

Prefer one page? guide.html is this whole kit in a single standalone file, built from these Markdown files by build-guide.py. Re-run the script after editing a card.

There is no grading script. The point is to watch the method work:

  • the engine asking instead of guessing;
  • a reviewer agent finding gaps before you do;
  • a plan gate that stops code until a human says yes;
  • your answers in step 02 turning up, three stages later, in requirements and code.

What you'll learn

By the end you will have:

  • built a v2 workspace: a hub that holds the AI-DLC record, with code repos beside it;
  • run all five phases and 33 stages at enterprise scope, answering question files and passing human gates;
  • seen how steering files, the hub's memory/, and an AI-DLC plugin keep an engine inside each repo's recorded rules;
  • generated code into two brownfield repos and one greenfield repo, against a versioned contract, in two bolts;
  • copied the feature's decisions back into each repo so they outlive the feature.

Step 01

Build the hub workspace and its three sibling repos

Runbook section: 01 · Workspace setup · Phase: before the lifecycle · Time: 30–40 minutes, once

Goal

Build, by hand, the layout AI-DLC v2 uses for a feature that spans several repos:

  • a hub folder, which is its own git repo and holds the AI-DLC record;
  • the code repos cloned beside each other inside it.

You'll do this by hand instead of running a script, because the layout is the lesson: - where each file lives decides who can see it; - it decides what gets committed where; - it decides what outlives the feature.

Who's in the room

The tech lead, alone, once per workspace. Nobody approves anything yet.

Do it

All commands are Windows PowerShell. $kit is wherever you cloned this course; change it.

1. Install the tools (once per machine).

# AWS's AI-DLC CLI. Run from a normal (not admin) PowerShell window.
irm https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.ps1 | iex
# Open a NEW terminal so PATH picks it up, then:
aidlc --version          # aidlc 2.11.0 (runtime 2.11.0)

# One or both engines
npm i -g @anthropic-ai/claude-code    # then sign in: claude
npm i -g @openai/codex                # needs 0.145.0 or newer; sign in: codex login

2. Make three "remote" repos. In a real team these are on GitHub. Here they're local folders that stand in for GitHub. That way the whole exercise runs offline, and you don't need SSH keys.

$kit  = "D:\path\to\ai-dlc-course"          # <- your course clone
$root = "D:\aidlc-practice"
mkdir "$root\remotes"
robocopy "$kit\prior-auth-api" "$root\remotes\prior-auth-api" /E /XD node_modules .claude
robocopy "$kit\prior-auth-web" "$root\remotes\prior-auth-web" /E /XD node_modules .claude
robocopy "$kit\runbook\practice\seed\prior-auth-notify" "$root\remotes\prior-auth-notify" /E
foreach ($r in 'prior-auth-api','prior-auth-web','prior-auth-notify') {
  git -C "$root\remotes\$r" init -b main
  git -C "$root\remotes\$r" add -A
  git -C "$root\remotes\$r" commit -m "seed: $r"
}

prior-auth-notify starts almost empty: steering files, a decision log, and an empty src/. It is the greenfield repo. The engine writes its code in step 08.

3. Create the hub and let AI-DLC clone the siblings.

mkdir "$root\prior-auth-workspace"; cd "$root\prior-auth-workspace"
git init -b main
Copy-Item "$kit\runbook\practice\seed\repos.json" .     # edit the url paths if your $root differs
aidlc system workspace-sync

repos.json declares the repo set. Each entry has a url, because without one AI-DLC clones git@github.com:<org>/<name>.git over SSH.

4. Configure the engine and check the setup.

# Claude Code
aidlc config --harness claude --yes
aidlc doctor

# Codex CLI: the same hub can hold both engines
aidlc config --harness codex --yes
aidlc doctor
codex          # first run only: type /hooks, press t to trust all, then Esc

5. Install each repo's dependencies.

foreach ($r in 'prior-auth-api','prior-auth-web','prior-auth-notify') {
  Push-Location $r; npm install; npm test; Pop-Location
}

6. Teach the hub to respect each repo's rules. Open aidlc\spaces\default\memory\project.md. Paste each block from $kit\runbook\practice\seed\memory-project-steering.md under the heading of the same name: Way of Working, Forbidden, Mandated. Then commit the hub:

git add -A; git commit -m "hub: repos.json, aidlc config, repo steering"

7. (Recommended) Install the learning helpers. Follow extensions/README.md. It takes about 10 minutes and gives you: - aidlc-coach, which explains where you are; - repo-plan-reviewer; - the decision-log guard; - the prior-auth-pack plugin.

What you'll see

workspace-sync clones the three repos and writes two generated files:

aidlc workspace-sync: reconciling D:\aidlc-practice\prior-auth-workspace against repos.json (3 repo(s))
  ✓ cloned prior-auth-api on 'main'
  ✓ cloned prior-auth-web on 'main'
  ✓ cloned prior-auth-notify on 'main'
  ✓ .gitignore managed block → 3 child dir(s)
  ✓ aidlc.code-workspace → 3 child root(s)
✓ workspace in sync

aidlc doctor before your first chat in the folder:

0 problems, 3 warnings.

The three warnings are expected: - "update cache is absent"; - "hooks have not run in this project yet" (they run on your first chat); - "uncommitted change(s) under aidlc/" (until you commit).

Under the hood

Open these and look; nothing here is magic.

  • .gitignore. A managed block lists /prior-auth-api/ and the other two. The hub never commits application code; each sibling has its own .git.
  • aidlc\spaces\default\memory\, which holds org.md, team.md, project.md and phases\. This is the method, loaded into every stage of every intent.
  • .claude\settings.json, AI-DLC's hooks:
  • plan-approval-guard, state-transition-guard and write-audit-log;
  • a Stop hook that keeps the workflow moving;
  • the status line. You don't write these; you learn what they do.
  • .claude\CLAUDE.md starts with @.claude/rules/aidlc.md. That one line is how the method reaches Claude's context.
  • On Codex the same onboarding goes to .codex\config.toml as developer_instructions. .codex\onboarding.md holds the same text for you to read.

Before you move on

  • Do all three repos' npm test runs pass? You're about to ask an engine to change them. You need to know the starting point is green.
  • Does project.md have the Repo steering paragraph under Way of Working? Step 02 is where you'll see it working.

Try this

Run aidlc doctor --verbose and read the check names. They are the setup's own checklist: hooks, harness, runtime, workspace records.

Files written

repos.json · .gitignore (managed block) · aidlc.code-workspace · .claude/ or .codex/ · aidlc/spaces/default/memory/*. Compare with reference-run/hub/.

Common snags (hit during the reference run)

  • aidlc is not recognized. The installer added it to your user PATH. Open a new terminal.
  • git commit fails with "Please tell me who you are". Set git config --global user.name and user.email first.
  • LF/CRLF warnings on commit. These are harmless in themselves, but on Windows, core.autocrlf=true makes Git check files out with CRLF endings. In the reference run, that broke U1's own gate after a checkout: Prettier flagged 84 files, all of them for line endings only. The fix that worked is a one-line .gitattributes in each repo: * text=auto eol=lf. The notify seed ships with it. For prior-auth-api and prior-auth-web, the engine adds it during Construction (step 08), or you can add it yourself after cloning.
  • The engine's shell says "The command line is too long". Your PATH is very long. Start the engine from a terminal with a shorter PATH.
  • Headless claude -p ignores the project's permissions. It needs the workspace trusted first. Open claude interactively in the hub once and accept the trust dialog.
Step 02

State the intent, pick the scope, get the brief approved

Runbook section: 02 · Intent and scope · Phase 0 Initialization + Phase 1 Ideation · stages 0.1–1.7 · Time: 60–90 minutes

Goal

Describe the work in one paragraph and let AI-DLC turn it into an approved initiative brief. You'll see three things for the first time:

  • the engine creates the intent record by itself;
  • it asks questions in a file;
  • every stage ends at a human gate, with an AI reviewer's findings already on the table.

Who's in the room

  • Product owner: owns scope and the final say.
  • UM director: owns the clock and the outcome.
  • Nurse lead: owns who is alerted.
  • Compliance lead: owns the regulatory reading and privacy.
  • Tech lead: owns feasibility and team.

Running solo, you play every seat. Keep answers/mob-answer-sheet.md open, and put the role after each answer.

Do it

Start the engine at the hub root (D:\aidlc-practice\prior-auth-workspace), never inside a sibling repo.

# Claude Code: run `claude`, then type
/aidlc --scope enterprise Urgent prior auth requests get a 72-hour determination clock: urgent requests jump the nurse review queue, providers and members are notified when a determination exists, and an at-risk alert fires before the clock runs out. Spans prior-auth-api, prior-auth-web and a new prior-auth-notify service.

# Codex CLI: run `codex`, then type
$aidlc --scope enterprise Urgent prior auth requests get a 72-hour determination clock: urgent requests jump the nurse review queue, providers and members are notified when a determination exists, and an at-risk alert fires before the clock runs out. Spans prior-auth-api, prior-auth-web and a new prior-auth-notify service.

Name the scope. With no --scope, AI-DLC v2.11 uses classic. Classic skips Ideation and Operation, which are the stages this feature needs. Enterprise runs all 33 stages at comprehensive depth.

Avoid % in the intent text on Windows.

Answering. At each question file the engine offers three ways to answer:

  1. Guide me — up to four questions at a time, in chat.
  2. I'll edit the file — you fill in [Answer]: tags yourself.
  3. Chat — talk it through and let the engine extract the decisions.

Pick 2 for this step at least once. Open the file in your editor, fill in each [Answer]: with a letter and a reason, add the role in brackets, save, and reply done.

At each gate reply in plain words: Approve, or Request Changes: <what and why>.

What you'll see

From the reference run. Your wording will differ.

Initialization runs without a gate. The engine creates aidlc/spaces/default/intents/261011-urgent-auth-clock/ and records all three repos in intents.json:

{ "slug": "urgent-auth-clock", "dirName": "261011-urgent-auth-clock",
  "scope": "enterprise",
  "repos": ["prior-auth-api", "prior-auth-notify", "prior-auth-web"],
  "status": "in-flight" }

You never typed --repos. The engine found the siblings on disk.

The question file cites your steering. The top of intent-capture-questions.md lists its sources. The hub rules you pasted in step 01 are there:

- [memory:M1] aidlc/spaces/default/memory/project.md#Forbidden: "NEVER change a rule
  recorded in a repo's docs/decisions.md (e.g. prior-auth-api D-001 ...)"

The engine pushes back when an answer collides with a recorded rule. In the reference run, the room said the at-risk alert should carry the request's urgency. The engine stopped and asked a new question before writing anything:

In Q12 you said the at-risk alert should carry whether the request is urgent. That conflicts with a recorded rule: notices and event payloads carry status and referenceId only (prior-auth-api D-003, decided with privacy office review). [...] recorded rules can't be changed in this workflow.

The room's answer distinguished notices to members and providers, which D-003 covers, from an alert to nurses. It recorded the decision as pending privacy-office confirmation, with a fallback. See the answer sheet.

A summary to confirm before anything is generated. The engine restates every answer as a list ("Problem and trigger", "Urgency", "Clock start", ...). It asks Looks correct / Request changes before writing intent-statement.md. Read it as carefully as the documents; it is what they will be built from.

An AI reviewer before the human gate. At enterprise scope, a product-lead reviewer agent reads the output and raises numbered findings. The reference run got six:

ID Severity Finding (short)
R-01 Major "Nurses cannot see urgent work today" is stated as fact; no answer said so
R-02 Major The privacy-office dependency isn't listed as an open question, and there's no fallback
R-03 Major Standard requests and "clock not started" requests are never measured
R-04 Minor The rule is already in effect; the text says "will take effect"
R-05 Minor Jargon with no glossary
R-06 Minor Nurse lead missing from the stakeholder table

The engine then gave its own view: it agreed with R-01 and R-02, and said R-03 and R-04 need facts only the humans have.

The room replied Request Changes with those facts. The engine recorded them as new answers Q16–Q19, asked for a fresh confirmation, revised, and sent the result back to the reviewer.

Under the hood

  • aidlc-state.md in the intent folder holds the current phase, stage and status. Open it between replies and watch it move.
  • audit/<host>-<clone>.md gets a row for each human turn (the record-human-turn hook) and each gate decision. "Who decided" lives here, not in chat.
  • ideation/intent-capture/memory.md holds the stage's working notes.
  • On Claude Code, the status line shows phase · stage · gate. /aidlc --status prints the same at any time.

Before you say Approve

  • Is every statement in intent-statement.md traceable to an answer, a [desc]/[memory] source, or a confirmed assumption? Each line carries a source tag; spot-check three.
  • Is each open decision listed with an owner?
  • Do any of the success metrics allow gaming? For example, a clock that starts "when complete" can be met by never marking requests complete.
  • Does anything quietly change a recorded rule (D-001, D-002, D-003)?

If you installed the helpers, type /aidlc-coach (Claude) or $aidlc-coach (Codex) at any gate for a one-minute briefing on what to check.

Try this

At the first summary confirmation, reply Request changes: the clock starts when the request is received. Then watch what happens: - the engine reopens the question and updates the summary; - later, the requirements in step 04 inherit the new start time; - the audit trail records the change.

Change it back, or don't, and see how far the change travels.

Then: the rest of Ideation (1.2–1.7)

Market research, feasibility, scope definition, team formation and rough mockups follow the same rhythm: questions, a summary, documents, a review, the gate. Stage 1.7 Approval & Handoff produces initiative-brief.md. That is the go/no-go.

Rally: after 1.7 is approved, a human creates the Rally Feature from the brief. AI-DLC does not talk to Rally.

Files written

All under aidlc/spaces/default/intents/<id>/:

  • aidlc-state.md and audit/
  • ideation/intent-capture/: intent-statement.md, stakeholder-map.md, intent-capture-questions.md
  • the rest of ideation/: build-vs-buy, feasibility, scope document, RAID log, team, mockups, initiative-brief.md

Compare with reference-run/hub/aidlc/.

Common snags

  • "Your answer didn't reach AI-DLC. Please give it once more." A reply was dropped between the chat and the engine's state tool. Repeat it. If it happens twice, run /aidlc --doctor.
  • The engine adds follow-up questions (Q12, Q13, ...). That's correct behaviour, not a loop: your answer opened a new question. Answer it.
  • Enterprise scope is thorough and slow. Each stage has questions, a summary, a review, and a gate. Budget an hour for Ideation. For a quicker first pass, use feature scope. It runs the same 33 stages at standard depth.
Step 03

Read every brownfield repo before anyone designs

Runbook section: 03 · Read the repos · Phase 2 Inception · stages 2.1 Reverse Engineering, 2.2 Practices Discovery · Time: 30–45 minutes

Goal

Watch AI-DLC build semantic context for code it didn't write. Before any requirement is written, the engine scans each existing repo. It writes nine documents per repo into a store the next feature can reuse. You, as each repo's lead, check that the documents describe the code that is actually there.

Who's in the room

  • api lead: checks codekb/prior-auth-api/.
  • web lead: checks codekb/prior-auth-web/.
  • Tech lead: approves the practices promoted into the method.

Do it

Nothing new to type. After stage 1.7 is approved, the engine moves into Inception by itself. If you closed the session, resume:

# Claude Code
/aidlc

# Codex CLI
$aidlc

At each gate: Approve, or Request Changes: <what the scan got wrong>.

What you'll see

From the reference run (stage 2.1; nine files per repo, about 2,300 lines across the three).

The scan said what is not there, which is the point. prior-auth-api has services and entities but no HTTP layer, and its api-documentation.md says so instead of inventing one:

| HTTP/REST endpoints | Not implemented | 0 |
... there is no router, controller, HTTP framework, OpenAPI document or request handler

The recorded rules and the known gaps were found. business-overview.md cites D-001, D-002 and D-003. code-quality-assessment.md lists the two seeded gaps by name: F-05: Open, undecided re-score rule and F-07: Overloaded PENDING status.

The web scan described what the app actually calls: nothing yet.

| GET /auth-requests on prior-auth-api | src/data/sample.ts:3 comment: "Static sample rows
  until the queue is wired to GET /auth-requests." | Not implemented: no HTTP client, no
  fetch, no data-fetching library, no base URL ... |

The greenfield repo was scanned too, and that's a difference from the runbook. The runbook expects nothing to scan in prior-auth-notify. AI-DLC v2.11 wrote its nine files anyway. It kept "what the steering commits the service to" apart from "what exists":

No business functionality is implemented. Everything below under "Committed Functionality" is what the steering commits the service to, not behaviour that exists.

The gate offered only Approve or Request Changes. It pointed the reviewer at code-quality-assessment.md and architecture.md in each repo.

Under the hood

  • A two-step pipeline: a developer agent scans the code, then an architect agent writes the documents. Watch for the Task / subagent calls in the transcript. On Claude Code, /aidlc-replay lists them after the fact.
  • Where it lands: aidlc/spaces/default/codekb/<repo>/. That is the space, not the intent. A later feature that touches prior-auth-api finds this store and reuses it if the code hasn't moved.
  • prior-auth-notify is scanned too, even though it's greenfield. Its codekb records the repo's commitments (from AGENTS.md) as "committed, not built". Check that it never presents a commitment as working code.
  • 2.2 Practices Discovery asks three inspector agents to review the draft practices independently: quality, developer, devsecops. After approval, the practices are promoted into memory/team.md and memory/project.md. Open project.md before and after; the diff is the lesson.

Before you say Approve

Open each repo's codekb folder next to the code. For prior-auth-api:

  • Does business-overview.md state the three recorded rules (D-001 >= 0.85, D-002 eligibility first, D-003 status and referenceId only)?
  • Does code-quality-assessment.md mention the known gap? AuthStatus.PENDING is overloaded, and re-scoring after a determination is undecided.
  • Does api-documentation.md describe an API that exists? Today prior-auth-api has no HTTP layer: services and entities only. A scan that invents endpoints is wrong.

For prior-auth-web:

  • Does api-documentation.md say what the web app calls? Today it reads static sample rows (src/data/sample.ts) and calls nothing live. This is where contract drift between repos first shows up.

Try this

Ask, before approving: What did you NOT read in prior-auth-web, and why? The answer tells you how the scan bounded itself. Bounding the scan is a deliberate token budget: AI-DLC's "semantics per token" idea.

Files written

  • For each scanned repo, in aidlc/spaces/default/codekb/<repo>/:
  • business-overview.md, architecture.md, code-structure.md
  • api-documentation.md, component-inventory.md, technology-stack.md
  • dependencies.md, code-quality-assessment.md, reverse-engineering-timestamp.md
  • From 2.2: the practices draft in the intent's inception/practices-discovery/, promoted into memory/team.md and memory/project.md.

Common snags

  • Cost spike at the phase boundary. Moving from Ideation into Inception and running the scans was the most expensive single step of Inception so far: roughly a quarter of all engine usage up to the codekb gate. This is expected for three repos at enterprise depth.
  • The codekb is not in the intent folder. Look in aidlc/spaces/default/codekb/, not under intents/<id>/inception/.
Step 04

Turn the intent into requirements, one answered question at a time

Runbook section: 04 · Requirements · Phase 2 Inception · stage 2.3 Requirements Analysis (Mob Elaboration) · Time: 45–60 minutes

Goal

This is Mob Elaboration, the ritual AI-DLC is best known for. The AI drafts the questions, and the room answers them. Every answer lands in a file and in the audit trail.

The cross-repo questions get settled here, while changing your mind is cheap: - which repo computes the clock; - which repo stores it; - which repo emits each event.

Who's in the room

The whole mob: - the product owner, the UM director and the nurse lead; - compliance; - all three repo leads.

If you're alone, read each question aloud and ask "whose call is this?" before answering.

Do it

Resume the workflow if needed (/aidlc or $aidlc). When the questions file appears, try Guide Me this time: the engine asks up to four questions at a time in chat. The file stays the source of truth whichever mode you pick.

The decisions this step must produce, with the answers the reference run gave:

Question Reference answer Seat
When does the clock start? When the request is complete; "clock not started" before that UM director + compliance
Which repo owns the clock? prior-auth-api computes decisionDueAt; web and notify only read it api lead
Queue order URGENT first, then decisionDueAt ascending Nurse lead
Events determination.issued {referenceId, status, issuedAt}; sla.at-risk {referenceId, urgency, decisionDueAt} 24h before due api lead + compliance
Old clients urgency defaults to STANDARD; decisionDueAt is null until complete api lead

What you'll see

From the reference run (stage 2.3). The questions file had 17 questions in four groups: The clock, Ownership and the local run, Reporting, and Recording rules and quality targets. The engine had settled the easy questions earlier, so these were the hard ones.

Ownership questions arrived on their own. Without being asked, the engine put the repo-crossing decisions up front, each with a "who owns it" option:

### Q10. Who decides the queue order, and how does prior-auth-web get the queue in the local run?
A. prior-auth-api owns the order and serves a small local read of the queue (C-1 rows,
   already ordered), defined in contract v1.1.0. prior-auth-web shows rows in the order it
   is given and never re-sorts. The countdown is display only ...
B. prior-auth-api publishes C-1 only; prior-auth-web sorts by the recorded order rule

It planned around the real code it found in step 03. The codekb said prior-auth-api has no HTTP server. So instead of inventing one, the options were concrete and local:

  • events travel as a JSON-lines file from api to notify (Q7);
  • the at-risk check is an api command that takes "now", so a test can control the clock (Q5);
  • reports come from an api export command (Q12).

Precision you would not have thought to ask for. For example:

  • Q1: "7 calendar days" became exactly 168 elapsed hours, with no time-zone dependency.
  • Q2: a determination issued exactly at the due time is on time (inclusive), tested at the boundary and 1 ms either side.
  • Q4: a second "mark complete" is refused with a typed error, and never restarts the clock.
