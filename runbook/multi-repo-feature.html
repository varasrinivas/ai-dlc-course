The feature: urgent requests get a 72-hour clock

The utilization management director wants urgent prior auth requests decided inside 72 hours, with nurses seeing those requests first and providers notified the moment a determination exists. Three repos have to change together, and one of them doesn't exist yet.

Regulatory context For Medicare Advantage, Medicaid and CHIP, and exchange plans, the CMS Interoperability and Prior Authorization rule (CMS-0057-F) sets 72 hours for expedited and 7 calendar days for standard decisions from January 1, 2026. Your compliance team owns the exact reading, including when the clock starts. regulation · confirm with compliance

Where Markdown lives: three homes, one rule each

The most common multi-repo mistake is putting the feature record inside one of the service repos. The other repos can't see it and it outlives the feature. AI-DLC v2 avoids this with a workspace: a folder that holds the AI-DLC record, with each code repo cloned beside it.

Home 1 · the hub

prior-auth-workspace/aidlc/

Rule: everything about the feature. Its own git repo.

  • The intent record: state, audit, every stage artifact
  • Per-repo code knowledge (codekb/<repo>/)
  • Team method (memory/) and standards (knowledge/)

AWS v2 layout

Home 2 · each code repo

prior-auth-*/

Rule: everything that must outlive the feature.

  • Code and tests (generated into the repo, never the hub)
  • Steering: AGENTS.md, with CLAUDE.md importing it
  • docs/decisions.md: durable domain decisions, copied over from the hub's ADR log at close-out

code in sibling repos ADR copy-over

Home 3 · Rally

tracking/rally/ → Rally

Rule: a mirror for reporting, never the source of truth.

  • The AI drafts an import file; a human imports it
  • Rally IDs come back into one map file
  • State moves at human gates, not on AI activity

course convention · AWS ships no Rally/Jira integration

The steering-file question

You start the engine from the hub, but each repo's rules live in that repo's AGENTS.md and docs/decisions.md. Nothing guarantees an engine running from the hub reads a nested repo's steering file before editing that repo. Say it explicitly, once, in the space's method file. Every stage of every intent loads it. course convention

aidlc/spaces/default/memory/project.mdadd this section
## Repo steering (multi-repo)
Before planning or changing code in a sibling repo, read that repo's
AGENTS.md and docs/decisions.md. They outrank anything in this file
for that repo. Never change a rule recorded in docs/decisions.md
(e.g. D-001: score >= 0.85 auto-approves) — raise it as a question.
One unit of work = one repo. Cross-repo coordination goes through
the contract in prior-auth-api/contracts/, never shared source.

Why enterprise and not feature or classic

ScopeStagesFit for this feature
enterprise33, comprehensive depth, strict Guard PolicyChosen: PHI, a regulatory deadline, three deployables, and Operation stages you'll need (SLO, alarms, rollback).
feature33, standard depthFine if compliance doesn't need comprehensive artifacts.
classic18, v1-style; no Ideation, no OperationLoses the deploy and observe stages that this feature's SLA depends on.

Choosing the scope is team decision. The stage counts are AWS v2. You can change scope mid-run with /aidlc --scope <name>.

Reverse Engineering runs as a two-step pipeline: a developer agent scans the code, then an architect agent writes nine files. For a multi-repo intent, each repo needs its own complete scan before approval. The output goes to a space-level store per repo, not the intent folder, so the next feature reuses it if the store is still current. AWS v2

2.2 Practices Discovery drafts the team's practices. A quality inspector, a developer inspector, and a devsecops inspector each review the draft without seeing the others' notes. After approval the practices are promoted to memory/team.md and project.md. This is where the repo-steering rule from step 01 gets confirmed. AWS v2

Review tip Have the web lead check that codekb/prior-auth-web/api-documentation.md describes the API the web app actually calls, not the API's own docs. Contract drift between repos shows up here first.

Domain Design writes components.md and an ADR log, decisions.md. Units Generation writes the units, their dependency graph, and the unit-to-story map, and tags each unit with a kind (service, ui, spec, …), which decides which design documents it owes. Contract Design writes contract-summary.md, the inter-unit contracts. AWS v2

Two rules that make multi-repo work 1. One unit = one repo. During Construction each git operation is anchored to one repo, so a unit that spans two repos fights the engine. course convention, follows from AWS v2's per-repo anchor
2. The contract is two artifacts. contract-summary.md in the hub is the design record. The machine-readable contract (prior-auth-api/contracts/) is code that U1 generates, and consumers pin its version. course convention
inception/contract-design/contract-summary.mdexcerpt

In v2 a bolt is a delivery slice covering one or more dependency-linked units. bolt-plan.md records the grouping and the reasons without changing the dependency graph. With the walking skeleton on, the first unit is built first as the smallest slice that works end to end, and a human approves it before any later unit starts. AWS v2

The per-repo branch and PR

The engine anchors each git operation to one repo. On top of that, use the same branch name in every repo and put the Rally ID and the intent path in each PR. A reviewer in any repo can then find the whole feature. course convention

Close-out: make the feature's decisions outlive the feature

The intent record stays in the hub. Each repo, though, needs the decisions it must keep honoring. Copy every ADR from domain-design/decisions.md that constrains a repo into that repo's docs/decisions.md as a new entry linking back to the intent. Then fold any new cross-repo practice into memory/project.md. course convention

**Decision:** decisionDueAt = completeAt + 72h for URGENT, + 7 calendar

**Why:** regulatory timeframe as read by compliance; one owner prevents
