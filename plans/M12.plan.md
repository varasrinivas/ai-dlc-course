## Objectives

After this module, the learner can:

1. Explain why brownfield work requires semantic context building: existing systems
   embed decisions their code never states, and an AI without them bulldozes constraints.
2. Produce a semantic map: entities, flows, invariants, and undocumented constraints
   flagged for human confirmation — validated by someone who knows the system.
3. Apply the semantics-per-token principle: record what constrains future changes, skip
   what any reader can re-derive; one confirmed invariant line beats 500 lines of pasted
   code.
4. Run a semantic survey with either engine and judge the output's density.

## Concept outline

1. **Why brownfield needs a survey** (`<h2>`)
   - Existing systems embed decisions the code never states: flag semantics, timing
     assumptions, "empty body means unknown member" conventions.
   - The AI's failure mode without them: syntactically perfect changes that violate
     invariants nobody restated (the M10 asymmetry, now concrete).
   - The survey is M10's brownfield default and M11's semantic-survey stage — M12 is
     how to actually run it: AI drafts the map from code + history + configs; humans
     confirm what the AI can only suspect.
2. **The semantic map** (`<h2>`)
   - Four sections: entities (with their real meanings, not their schemas), flows (who
     calls what, when), invariants (what must stay true), flagged unknowns (suspected
     constraints awaiting a human yes/no).
   - The flagging discipline is the map's integrity: the AI marks "E4 handling suggests
     retro-termination — CONFIRM" rather than asserting; a confirmed map line carries
     its confirmer's name.
   - Exit criterion (M11): validated by an engineer who knows the system — the retiring
     engineer's knowledge becomes an artifact this month, not a eulogy in May.
3. **High semantics-per-token** (`<h2>`)
   - The economics: context windows are finite and shared; raw code is low-density
     context ("what the system does" restated at 1:1 scale).
   - The map compresses meaning: "eligibility data ≤ 24h stale (nightly 02:00 refresh)"
     is one line that answers M05's staleness question forever; the code path that
     implies it is 500 lines across two repos.
   - Curation heuristics: record invariants, surprises, and semantics ("what E4 means");
     skip what any reader re-derives (getters, DTOs, framework noise). Density is why
     the map gets read — by engines and by humans.

## Recap bullets

1. Brownfield systems embed decisions their code never states; changing them without a
   survey is how syntactically perfect diffs violate real invariants.
2. The semantic map has four sections — entities, flows, invariants, flagged unknowns —
   and its integrity is the flagging discipline: the AI suspects, humans confirm.
3. Semantics-per-token is the quality bar: record what constrains, skip what any reader
   re-derives; one confirmed line can answer a question forever.
4. The map's exit criterion is human validation — tribal knowledge becomes an artifact
   while its holders are still in the building.
5. Next → M13 · Context Memory Across the Lifecycle — where all these artifacts live.
