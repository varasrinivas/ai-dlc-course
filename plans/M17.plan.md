   (mutations), what's flatly denied — allowlists in settings, permission modes.
2. Write hooks that fire gates on events: a PostToolUse hook running tests after
   edits; a PreToolUse hook blocking guardrail-file edits without a decision record.
3. Design an approval topology: human gates only where M02's decision table puts
   them; machine gates everywhere else; avoid alert fatigue (the checkpoint budget).
4. State the honest engine difference: Claude Code enforces via hooks + permissions;
   Codex CLI via approval modes + sandboxing — same gates, different mechanisms.

## Hook

Friday's retro surfaces an uncomfortable moment: during Wednesday's rush, someone
approved an engine suggestion that edited `config/threshold.json` — the 0.85 — and
nobody noticed until the diff review caught it. Nothing shipped; the guardrail held at
the human gate. But the team's conclusion is the right one: "We got lucky. The rule
lived in a file the engine reads and a habit we almost kept." By Monday the rule lives
somewhere better: a hook that physically blocks any edit to that file unless a signed
decision record exists, and a permission model that makes the engine ask before
touching config at all. Discipline caught it once. Mechanism catches it every time.

## Concept outline

1. **The permission model** (`<h2>`)
   - Claude Code's default posture: read freely, ask before mutating (edits, bash);
     allowlist safe commands in settings (`.claude/settings.json` permissions), keep
     mutations behind prompts.
   - Permission modes as postures: default (ask), acceptEdits (trusted loops), plan
     (read-only — M15), bypass (never for guardrail repos; say why).
   - Tuning principle = M02's table applied to tooling: the exposure boundary gets a
     human every time; reversible low-blast actions flow freely.
2. **Hooks: gates as code** (`<h2>`)
   - Hooks fire on engine events — before a tool runs (PreToolUse: can block), after
     (PostToolUse: can validate), at session stop. They are configuration, not hope.
   - Two canon hooks: PostToolUse → run jest after src edits (M16's "engine runs
     gates," now unskippable); PreToolUse → refuse edits to config/threshold.json
     unless docs/decisions/ contains a matching record (M14's rule, now physical).
   - Hooks output → the engine reacts: a failing hook sends the loop back to iterate;
     the human sees only work that survived the machines (M08's ordering, mechanized).
3. **Designing the approval topology** (`<h2>`)
   - Place human gates exactly where the decision table says: guardrail files,
     deploys, PHI egress — and almost nowhere else.
   - The checkpoint budget: every prompt-for-approval spends attention; gate
     everything and humans rubber-stamp (alert fatigue is how real gates die).
   - Machine gates are free and tireless — spend them lavishly; human gates are
     scarce — spend them where blast radius lives. Audit the topology per bolt close.

## Lab outline

**Lab M17 · 30 min · practitioner**

- **Path A — Understand It:** artifact = a hooks + permissions config (JSON excerpt:
  permissions allowing `npx jest` / read-only git freely; PreToolUse matcher on
  config/threshold.json running a check script; PostToolUse jest hook) plus a
  three-line narration of an attempted threshold edit. Trace: what fires, in what
  order, what the engine sees, where the human enters. 3 check questions + answers
  (incl. the alert-fatigue question: which of the allowed commands would be WRONG to
  gate, and why).
- **Path B — Build It with AI (both engines):** unit of work — *mechanize two gates,
  then drill them*.
  - Claude Code: engine writes `.claude/settings.json` permissions + two hooks (a
    PowerShell check script for the threshold file; a jest PostToolUse hook), then
    the drill: a fresh session is asked to bump the threshold — the hook must block;
    log to `docs/M17-gate-drill.md`.
  - Codex CLI: honest-parity variant — same two gates as (a) an approval-mode posture
    + AGENTS.md contract and (b) a `scripts/check-gates.ps1` the engine must run
    before presenting; same drill, same log.
  - Verify: drill shows the block/refusal; jest gate demonstrably ran; log has both.
    Parity note states plainly: same gates, different mechanisms — Claude Code
    mechanical, Codex contractual+scripted; this asymmetry is M22 input.

## Recap bullets

1. Permissions decide what the engine may do at all: read freely, ask before mutating,
   deny the unforgivable — the exposure boundary configured into the tool.
2. Hooks fire gates on events: PreToolUse can block (the threshold lock), PostToolUse
   validates (jest after every edit) — M16's convention made unskippable.
3. Failing hooks send the engine iterating; humans see only work that survived the
   machines — M08's gate order, mechanized.
4. Spend machine gates lavishly and human gates scarcely: alert fatigue is how real
   checkpoints die.
