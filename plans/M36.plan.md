## Hook

The compliance officer from M11 is back with the same request: "Show me the process, then show me
it was followed." Last year the answer was a folder of stage files and a per-bolt log, checked
against each other in four minutes. This year the portal team runs AWS's engine, and the tech lead
opens a folder she didn't write: `intents/`, a state file, an `audit/` directory with one shard per
machine. The officer points at a line in the shard that reads `GATE_APPROVED` and asks who typed
that. Then she asks a harder question: could the engine have typed it itself? The record is richer
than the old one. It can only answer the officer if the team can read it.

## Concept outline

1. **One intent, one record** (`<h2>`)
   - A space (`aidlc/spaces/default/`) holds every piece of work for one team. An intent is one
     piece of work, and its folder `intents/<YYMMDD>-<label>/` is created by the engine's own
     `intent-create`, not by the agent.
   - Initialization 0.1–0.3 (Workspace Scaffold, Workspace Detection, State Initialization) runs
     deterministically, with no gate. It writes `aidlc-state.md`, `project-description.json` and
     the first audit events (`WORKFLOW_STARTED`, `WORKSPACE_SCAFFOLDED`, `WORKSPACE_SCANNED`,
     `WORKSPACE_INITIALISED`), and classifies the hub as brownfield or greenfield.
   - Phase folders appear only for phases the scope runs; stage folders appear only when a stage
     writes something. A missing folder means "never planned", and the audit's `PHASE_SKIPPED`
     names it. Reverse Engineering writes to the space-level `codekb/<repo>/`, not the intent,
     because one view of a repo serves every intent (M38).
2. **State says where; audit says what happened** (`<h2>`)
   - `aidlc-state.md` is a manifest: scope, depth, Guard Policy, stage checkboxes
     (`[ ] [-] [?] [R] [x] [S]`), current stage. The engine rewrites it on every transition. It
     answers "where are we?", never "who decided?".
   - The audit is append-only and sharded per machine clone (`audit/<host>-<clone>.md`), so two
     people never fight over one file. 115 event types in 25 categories, each with one emitter.
     The agent may not write authority events (`GATE_APPROVED`, `STAGE_COMPLETED`,
     `HUMAN_TURN`…); the CLI refuses them.
   - A gate approval is a chain: `STAGE_AWAITING_APPROVAL` → `HUMAN_TURN` (the hook saw a person
     type) → `GATE_APPROVED`, with the person's own words in `Person Reply`.
   - The engine's own caveat, quoted from `audit-format.md`: audit shards are "operational
     evidence, not a tamper-proof human-authorship boundary". The answer to the officer's second
     question: the engine makes forging hard, git history makes it visible, and neither makes it
     impossible.
3. **Memory: five layers, one chain** (`<h2>`)
   - `org.md` → `team.md` → `project.md` → `phases/<phase>.md` → stage (reserved). Strict-additive:
     a narrower layer adds to a wider one and never silently overrides it; a contradiction is an
     error. A section holding only `<!-- … -->` comments counts as empty.
   - Where Prior Auth rules sit: the guardrails in `project.md` (M35); tests-first in `team.md`
     under Testing Posture (the engine's own advice in M35); nothing for now in `org.md`, which is
     the platform team's.
   - `knowledge/` is free-form domain knowledge the team adds (the criteria glossary would go
     there); `.claude/knowledge/` is the engine's methodology and read-only.
4. **What you commit, and where the decision log lives now** (`<h2>`)
   - Committed in the hub: `memory/`, each intent's record including `aidlc-state.md` and
     `audit/`, `codekb/`, `knowledge/`. Local only (the managed `.gitignore` block):
     `.aidlc-sessions/`, `active-space`, `active-intent`, `.aidlc-engine/`, runtime graphs.
   - `docs/decisions.md` stays in each repo. The engine records that a gate was approved; the
     decision log records the decision, its reason and the medical director's name. The rule from
     M34 holds: the engine keeps the book, people sign it.
   - The officer's four-minute check, rewritten: the stage file (`.claude/aidlc-common/stages/…`)
     against `aidlc engine audit history --event GATE_APPROVED`.

## Recap bullets

- An intent is one piece of work with one folder; the engine creates it, and Initialization runs
  without a gate.
- `aidlc-state.md` says where the work is; the audit shards say what happened. Read the audit with
  `aidlc engine audit history`, not by hand.
- A `GATE_APPROVED` block proves a person answered at that gate, in their words. It isn't a
  signature, and the engine says so.
- Memory is five layers, each adding to the one above it; the Prior Auth guardrails stay in
  `project.md`, and the decision log stays in each repo.
- Next: **M37, Scopes, depth and the composer.** Why `feature` was the right size for this intent,
  or wasn't.
