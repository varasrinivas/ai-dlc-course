## Concept outline

1. **One hub, many repos, many intents** (`<h2>`)
   - The hub is its own git repo; `repos.json` lists the code repos and `aidlc system
     workspace-sync` clones them beside it (M35, one sentence). The hub's `.gitignore` keeps their
     code out of the record.
   - An intent's repos are fixed at creation (`--repos`, or every sibling by default) and stored in
     `intents.json`. Show the real two-row file after the capture. No add-repo command in v2.11.0:
     a repo the intent didn't record means a new intent (or a fresh one with `--repos`).
   - Code changes still land per repo, on each repo's own branch; the hub commit holds only the
     record (M39's last step). Release order across repos is a team decision (the runbook's
     "deploy in contract order").
2. **One scan per repo, shared by every intent** (`<h2>`)
   - Reverse Engineering runs per repo and writes `codekb/<repo>/`, nine files, at the space level.
   - Before scanning, the engine checks freshness per repo (`codekb-scope-diff --repo <repo>`):
     `NO_STORE` (M38's first scan), `CURRENT` (reuse, a person may confirm), `STALE` (rescan). Show
     the real verdicts for the second intent.
   - Why it matters: the semantic map (M12) is a property of the repo, not of a feature. Two intents
     that read the same repo read the same map, and a stale map is caught before design starts.
3. **Teams, and the single-repo limit** (`<h2>`)
   - Team mode: each team owns a unit and approves its work; the engine projects a `Unit Progress`
     grid from the DAG. Valid only with unit-major.
   - The limit: "Team ownership requires the workspace root itself to be the source Git repository;
     intents with recorded sibling repos must remain solo." The real M38 line.
   - The workable arrangement for a hub: one conductor session; per-unit Plan Approval and
     checkpoints owned by the team whose repo it is; the contract (M38's Contract Design) as the
     coordination point; or, for fully separate team runs, one workspace per repo and the contract
     between them (the runbook's step 6).
4. **Rally as a human mirror** (`<h2>`)
   - No AWS integration; course convention, badged in the runbook. Mapping table from the runbook.
   - A person moves Rally at each gate. The engine never reads Rally, so Rally can never approve
     anything; the audit stays the record (M36), Rally is the program office's view of it.
   - Close of Track 8 for leaders: the list of human stops the engine keeps, one line each, M35–M40.

## Recap bullets

- One hub holds the record; the code repos sit beside it; each intent records its repos at creation.
- `codekb/<repo>/` is shared by every intent and freshness-checked before reuse.
- Team mode needs the hub to be the source repo; with sibling repos one session conducts, and the
  teams own the checkpoints and the contract.
- Rally mirrors the engine by hand; it never approves anything.
- The engine is an option: it schedules, records and checks. Every answer, gate, plan, checkpoint
  and grant stays human. End of course: back to the hand-run method whenever the engine isn't the
  right tool.
