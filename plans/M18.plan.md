## Objectives

After this module, the learner can:

1. Explain subagents: independent contexts spawned from a main session, doing scoped
   work and reporting back — M16's session hygiene by construction, in parallel.
2. Choose what to parallelize: disjoint units of work, exploration/research fan-outs,
   multi-lens reviews — and what never to (two agents in one file).
3. Run the orchestration: pin interface contracts before fan-out, assign scoped
   prompts, collect results, merge, run gates on the merged whole.
4. Apply merge discipline: a conflicting increment triggers a narrow re-plan, never a
   force-merge; the human checkpoint reviews the integrated result.

## Hook

Bolt 3 has two units of work that don't touch: the channel-preference lookup and the
undeliverable-notification routing. The engineer could run them as two sequential
sessions — ninety minutes each. Instead the main session becomes a foreman: it pins the
one interface both slices share, spawns two subagents with scoped prompts, and watches
them build in parallel — each in its own fresh context, neither able to smear into the
other's files. Forty minutes later it merges the two increments, runs the full gate
suite on the combined result, and presents one integrated diff for review. The
parallelism is real. So is the part that kept it safe: the interface was pinned
*before* the fan-out, not negotiated during the merge.

## Concept outline

1. **Subagents: fan out the work** (`<h2>`)
   - What they are: independent agent contexts spawned from the main session — own
     context window, scoped instructions, report back a result; the orchestrator
     integrates.
   - Why the isolation matters: each subagent is a fresh M16 session by construction —
     no residue, one concern; and a failed subagent costs its slice, not the bolt.
   - Three good fan-outs: disjoint UWs (build in parallel), exploration (search/read
     the estate from multiple angles), review lenses (one subagent per concern:
     criteria coverage, constraint compliance, PHI).
2. **Parallel units of work** (`<h2>`)
   - Parallelize only what's disjoint: M03's sizing rule makes UWs reviewable; add
     "touches different files" and they're parallelizable — the same slicing pays
     twice.
   - The orchestrator is a foreman, not a bystander: it pins shared contracts, writes
     each subagent's scoped prompt (context by pointer), collects increments,
     integrates.
   - Checkpoints don't parallelize away: subagent output is increment output — it
     meets the same review gate; parallel construction, serial accountability.
3. **Merge discipline** (`<h2>`)
   - Pin the seams first: interface contracts (DTOs, ports, function signatures)
     agreed and written down BEFORE fan-out; a subagent that needs to change a pinned
     contract stops and defers (plan→ask→defer at the seam).
   - Merge order and gates: integrate, then run the full suite on the merged whole —
     each slice green does not imply the union green.
   - Conflict protocol: a collision is a re-plan of the smaller slice, never a
     force-merge; log the collision — repeated seam conflicts mean the decomposition
     was wrong (feedback to Inception).

## Recap bullets

1. Subagents are fresh, scoped contexts fanned out from an orchestrating session —
   M16's hygiene by construction, and a failed slice costs a slice, not the bolt.
2. Parallelize disjoint UWs, explorations, and review lenses; never two agents in one
   file.
3. Pin the seams before the fan-out: interface contracts are written, signed context —
   a subagent that needs to change one stops and defers.
4. Gate the union: each slice green does not imply the merged whole green; conflicts
   re-plan the smaller slice, never force-merge.
5. Track 4 complete — next → M19 · Steering with AGENTS.md (Track 5: the same
   methodology on the second engine).
