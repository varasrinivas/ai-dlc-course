## Objectives

After this module, the learner can:

1. Describe the Construction pipeline for one unit of work: architecture proposal →
   implementation plan → code + tests → increment review, with checkpoints at plan
   approval and increment review.
2. Review an AI-proposed implementation plan: completeness, deferred decisions, and
   traceability to acceptance criteria.
3. Explain why code and tests are generated together, and verify test-to-criteria
   traceability in a diff.
4. Run one full Construction loop on the intake unit of work with either engine —
   enforcing the plan-approval checkpoint before any code exists.

## Hook

Thursday, 9:20 am. Bolt 1 opens with UW-1a — schema validation for `AuthRequest` intake —
and for the first time this course, code is about to exist. The AI posts three artifacts
in order: a proposed architecture (where validation lives, what it depends on), an
implementation plan (nine steps, two marked as decisions it won't make), and nothing else
— because the plan is a checkpoint, and no approved plan means no code. The junior dev
asks the obvious question: "It could have just written the code in the time this took."
True. And that's exactly how you get 4,200 lines nobody can explain — Construction's
discipline is that speed arrives *after* the plan survives contact with humans.

## Concept outline

1. **Architecture and plans before code** (`<h2>`)
   - Per unit of work, the AI proposes architecture (placement, dependencies, data flow)
     — small-scale, reviewable, not a cathedral document; then an implementation plan:
     ordered steps, each small enough to verify.
   - Plans carry their own deferred decisions inline ("step 6 blocked: outreach-log
     format — HUMAN"), continuing M02's protocol inside Construction.
   - Plan approval is checkpoint #1: cheap to redirect a plan, expensive to redirect a
     diff. "It could have just written the code" is the AI-managed reflex in disguise.
2. **Code and tests arrive together** (`<h2>`)
   - One loop produces both: implementation + tests that trace to the acceptance
     criteria by name (AC-1 → test name), not coverage theater.
   - The AI explains its own diff — every non-obvious choice annotated in the increment
     summary; "unexplained regex" from M03's log is the anti-example.
   - Small diffs by construction: UW sizing (M03) is what keeps understand-every-line
     honest at review time.
3. **Where the humans stand** (`<h2>`)
   - Checkpoint positions: plan approval (before code), deferred decisions (mid-loop,
     narrow blocks — only the affected step waits), increment review (before merge —
     the Mob Construction moment, ritual in M08).
   - What reviewers verify at increment review: criteria coverage, constraint compliance
     (decisions.md), and explanation quality — not style nits the steering file already
     owns.
   - Exit of Construction: increment merged + increment summary written to context memory.

## Bridge table

Columns: **The old way / Construction / What changed**:
| Design doc written once, ages quietly | Per-UW architecture proposal | Scoped to one checkpoint-sized slice; reviewed the day it's used |
| Code review after two weeks of work | Increment review per bolt | Small diff, author-explained, decider present |
| Tests written after (or never) | Tests generated with code | Trace to acceptance criteria by name — coverage you can audit |

## Recap bullets

1. Construction runs per unit of work: architecture proposal → implementation plan →
   code + tests → increment review — checkpoints before code and before merge.
2. The plan is the cheap place to be wrong; approving it is a human checkpoint, not a
   formality.
3. Code and tests arrive together, and tests trace to acceptance criteria by name —
   auditable coverage, not coverage theater.
4. The AI explains its own diff; reviewers verify criteria, constraints, and explanations
   — style belongs to the steering file.
5. Next → M08 · Mob Construction & Human Checkpoints — the review ritual itself.
