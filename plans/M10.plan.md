> Audience: **both** · ~30 min

## Objectives

After this module, the learner can:

1. Explain adaptive rigor: stage selection scaled to risk, with the full Track-2 pipeline
   as the ceiling and a human owning the dial.
2. Name the risk inputs — blast radius, reversibility, regulatory exposure (M02), plus
   novelty and size — and score a change against them.
3. Describe greenfield vs brownfield detection and what each default implies (greenfield:
   scaffold-and-go; brownfield: survey before touching — M12).
4. Assign a defensible stage list to a real change request, including which checkpoints
   survive even at minimum rigor.

## Hook

Three requests hit the portal team's queue the same morning. One: the outreach log
message says "elligible" — fix the typo. Two: clinical policy wants
`AUTO_APPROVE_THRESHOLD` moved to 0.82 for imaging requests. Three: build the
`ClinicalCriteria` scoring engine — bolt 2's centerpiece. Running the typo through full
Inception with a Mob Elaboration would be theater; running the threshold change without
one would be malpractice. Same team, same day, three different ceremonies — and the
skill of this module is saying *which* and *why* out loud, before the work starts,
instead of letting habit or hurry decide.

## Concept outline

1. **Rigor is a dial, not a switch** (`<h2>`)
   - Track 2's pipeline is the maximum ceremony; adaptive rigor selects which stages a
     change actually needs — over-ceremony taxes every small change into the shadow
     queue ("we'll just slip it in"), under-ceremony is M01's anti-pattern.
   - The dial's inputs: M02's three (blast radius, reversibility, regulatory exposure)
     plus two new: novelty (has this shape of change been done here before?) and size.
   - The invariant: a human sets the dial. The AI proposes a rigor level with reasons;
     the skip decision is itself a checkpoint — and it's logged.
2. **Greenfield vs brownfield detection** (`<h2>`)
   - The AI reads the ground before proposing the process: empty repo / no conventions →
     greenfield defaults (scaffold, full Inception, establish steering); existing system →
     brownfield defaults (survey before touching — semantic context building, M12).
   - Detection signals: repo contents, test presence and shape, steering file existence,
     commit history density; misdetection cost is asymmetric — treating brownfield as
     greenfield bulldozes constraints nobody restated.
   - Prior Auth reality: the portal is greenfield, but it integrates with a 12-year-old
     eligibility system — most work is *mixed*, and rigor follows the riskier edge.
3. **Stage selection heuristics** (`<h2>`)
   - Worked spectrum: typo (construction loop + mechanical gates only; no Inception),
     threshold change (tiny diff, maximum rigor: policy decision, Mob Elaboration
     question, sign-off at exposure boundary, audit note — risk ≠ diff size),
     scoring engine (full pipeline, every stage).
   - Heuristic table: score the five inputs low/med/high → stage list; ties broken
     toward more rigor in regulated domains.
   - What never gets skipped: the mechanical gates (they're free) and one human
     disposition (someone owns every change, however small).

## Lab outline

**Lab M10 · 25 min · both audiences**

- **Path A — Understand It:** artifact = the three change requests as tickets, plus a
  five-input risk scorecard (blast radius / reversibility / regulatory / novelty / size).
  Trace: score each ticket, assign a stage list, name the one thing that never gets
  skipped. Check questions incl. the trap: why does the 1-line threshold change outrank
  the 400-line scoring engine on *one* axis (novelty is lower, but regulatory exposure
  and irreversibility-in-audit-terms dominate). Answers provided.
- **Path B — Build It with AI (both engines):** unit of work — *make the dial explicit*.
  Engine reads the repo + steering file and writes `docs/M10-rigor-policy.md`: a change-
  class table (docs-only / code-no-behavior / behavior-change / guardrail-or-PHI) mapping
  each class to required stages, gates, and who signs off; plus a "detection" section
  stating what the engine checked to classify this repo greenfield vs brownfield. The
  policy must state that guardrail-class changes always run the full pipeline. No code.
  - Claude Code / Codex variants: identical prompt.
  - Verify: four change classes present; guardrail class = full pipeline; detection
    section cites actual repo evidence; no code files. Parity: same table structure.

## Recap bullets

1. Adaptive rigor scales ceremony to risk: Track 2's pipeline is the ceiling, not the
   default — and skipping is a logged human decision, never a habit.
2. Five risk inputs: blast radius, reversibility, regulatory exposure, novelty, size —
   and risk does not equal diff size (the 1-line threshold change gets maximum rigor).
3. The AI detects greenfield vs brownfield before proposing a process; brownfield means
   survey before touching (M12).
4. Mechanical gates and one human disposition survive even minimum rigor.
5. Next → M11 · The Stage Library — the open-source catalog the dial selects from.
