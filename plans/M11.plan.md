## Objectives

After this module, the learner can:

1. Explain why AI-DLC ships as an open-source workflow definition — the process itself is
   inspectable, diffable text that engines can execute and teams can amend.
2. Read a stage definition: purpose, trigger heuristic, inputs, activities, outputs, exit
   criteria.
3. Connect decision heuristics on stages to M10's rigor dial — the dial selects stages;
   the heuristics are written on the stages themselves.
4. Author and register a new org-specific stage (a healthcare PHI-review stage) without
   forking the methodology.

## Hook

The compliance officer asks the question every regulated team eventually faces: "Where is
your SDLC documented, and how do I know the team actually follows it?" The old answer was
a wiki page dated three reorgs ago. The portal team's answer is a folder of stage
definitions — plain text files stating what each stage takes in, produces, and requires
before exit — plus per-bolt logs showing which stages ran and who signed each exit. The
officer reads the "deploy sign-off" stage, then bolt 1's close-out, and checks them
against each other in four minutes. A process that is text can be audited, executed, and
improved. A process that is habit can only be believed.

## Concept outline

1. **A workflow you can read** (`<h2>`)
   - AI-DLC's workflow is published as an open-source definition: the stages, their
     sequence options, and their decision heuristics are files, not folklore.
   - Three consequences: engines execute it (both Claude Code and Codex read the same
     stage text), auditors verify it (stage exit vs bolt log), teams diff it (process
     changes are reviewable PRs, not memos).
   - This is the steering-file idea at methodology scale — the process itself lives in
     context memory.
2. **Anatomy of a stage** (`<h2>`)
   - Six fields: purpose · trigger heuristic (when to include — M10's dial reads this)
     · inputs · activities · outputs · exit criteria (who signs).
   - Worked read: the "semantic survey" stage (trigger: brownfield detected; output:
     semantic map — M12) and the "mob elaboration" stage (trigger: behavior-change or
     higher; exit: approved UWs + recorded constraints).
   - Exit criteria are the load-bearing field: a stage without a checkable exit is a
     meeting, not a stage.
3. **Extending the library** (`<h2>`)
   - Org-specific stages extend, never fork: the portal team adds "PHI review" (trigger:
     guardrail-or-PHI class from M10's policy; output: an evidence pack for compliance).
   - Stage definitions are versioned like code; changing a trigger heuristic is a
     reviewed change with a rationale — the process improves by PR.
   - Restraint note: a library that doubles every quarter is process theater returning;
     new stages must earn their trigger.

## Lab outline

**Lab M11 · 25 min · practitioner**

- **Path A — Understand It:** artifact = two stage definitions in full six-field form
  (SEMANTIC SURVEY; PHI REVIEW). Trace: identify each field; decide which M10 tickets
  (T-101/102/103) trigger each stage; verify each exit criterion is checkable. 3 check
  questions + answers (incl.: T-102 triggers PHI REVIEW? — yes: guardrail class, even
  though no code touches PHI storage, the evidence pack documents the policy decision).
- **Path B — Build It with AI (both engines):** unit of work — *author and register the
  PHI-review stage*. Engine writes `docs/M11-stage-phi-review.md` with all six fields
  (trigger: guardrail-or-PHI class per docs/M10-rigor-policy.md; outputs: evidence pack
  — decision record, threshold audit note, access-scope diff; exit: compliance owner
  signs), then updates `docs/M10-rigor-policy.md` so the guardrail class lists the new
  stage. No code.
  - Claude Code / Codex variants: identical prompt.
  - Verify: stage file has six labeled fields; rigor policy now references the stage;
    diff touches only the two docs files. Parity: same fields and registration; wording
    differs.

## Recap bullets

1. AI-DLC's workflow is open-source text: stages, sequences, and heuristics are files —
   executable by engines, auditable by compliance, diffable by teams.
2. A stage is six fields — purpose, trigger, inputs, activities, outputs, exit criteria —
   and the exit criterion is what separates a stage from a meeting.
3. M10's dial reads the trigger heuristics written on the stages; selection is
   mechanical once the risk class is decided.
4. Extend, don't fork: org stages like PHI review sit beside the standard ones, versioned
   and reviewed — and every new stage must earn its trigger.
5. Next → M12 · Semantic Context Building for Brownfield.
