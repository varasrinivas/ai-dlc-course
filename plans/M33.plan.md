## Objectives

After this module, the learner can:

1. Map responsible AI dimensions (fairness, explainability, privacy & security,
   controllability, transparency, governance) onto AI-DLC's existing checkpoints —
   and name which gate owns which risk, instead of bolting on a separate review.
2. Identify the fairness failure modes of the auto-approval path (threshold drift,
   disparate match scores across member populations) and design the backstops:
   the nurse review queue, disparate-outcome tests, and human-only threshold changes.
3. Apply PHI-safe context hygiene: what may enter prompts, steering files, and
   context memory (decisions, synthetic fixtures) and what never may (member data).
4. Establish provenance and audit trails for AI-authored code and for every
   `Determination` — so accountability demonstrably stays with named humans.

## Hook

Four thousand two hundred requests auto-approved last month, and the compliance
officer's question is only seven words: "Who decided each one of those, exactly?"
The team's first instinct is to say "the criteria engine" — and that answer, they
realize as they're forming it, is the whole problem. An engine can't be
accountable. It can't sit in a deposition, can't explain a denial to a member's
family, can't sign the attestation the state auditor wants. The portal was built
by AI at bolt speed, and every one of those 4,200 determinations needs a human
name, a criteria version, and a match score behind it. The good news: AI-DLC
already built the scaffolding for that answer. This module makes it explicit.

## Concept outline

1. **Responsible AI is a lifecycle property, not a checklist** (`<h2>`)
   - The dimensions — fairness, explainability, privacy & security,
     controllability, transparency, governance — are not a new review stage;
     each one attaches to a checkpoint AI-DLC already has.
   - Inception owns fairness questions (Mob Elaboration asks "who could this
     harm?" alongside "what should this do?"); Construction owns controllability
     and transparency (understand-every-line, the chain); Operations owns
     drift monitoring and the audit trail.
   - The anti-pattern echo from M01: an AI-managed shop can't answer the
     compliance officer at all; an AI-assisted shop answers slowly. Oversight
     at checkpoints is what makes the answer fast *and* true.
2. **Fairness where it bites: the auto-approval path** (`<h2>`)
   - The 0.85 `AUTO_APPROVE_THRESHOLD` is a clinical-policy decision wearing a
     config variable's clothes: no engine may move it; a diff that touches it is
     a human decision surfaced at a checkpoint, never a silent optimization.
   - Match scores can differ systematically across member populations (criteria
     written against typical presentations under-match atypical ones); the nurse
     review queue is the fairness backstop — below threshold means a human looks.
   - Test for disparate outcomes the way you test for regressions: fixture
     cohorts, approval-rate assertions, alarms in Operations.
3. **PHI-safe context hygiene** (`<h2>`)
   - Prompts, steering files, plan files, and context memory are all context —
     and context leaves the building. Decisions and schemas belong in the chain;
     member data never does.
   - Practice-repo rule made explicit: fixtures are synthetic-only, and the
     steering file says so — the engine then enforces the rule on every future
     bolt (the steering file as a responsible-AI control surface).
   - Brownfield corollary from M12: semantic maps summarize structure, not
     records — high semantics-per-token is also a privacy property.
4. **Provenance: who wrote this code, who made this call** (`<h2>`)
   - Every `Determination` carries `matchScore`, `criteriaVersion`, and
     `decidedBy` (`"auto"` or a nurse identifier) — explainability as schema,
     not aspiration.
   - AI-authored code provenance is the chain (M13): the plan file names the
     human who approved it; "understand every line" (M08) is the moment
     accountability transfers to a person.
   - Accountability never transfers to the engine. The engine builds; the names
     on the checkpoint answer for the build.

## Lab outline

**Lab M33 · 25 min · both**

- **Path A — Understand It:** artifact = a responsible-AI gate review transcript:
  a reviewer walks the Bolt 2 criteria-matching diff and flags three findings —
  (1) a threshold tweak from 0.85 to 0.87 buried mid-diff with no decision-log
  entry, (2) a test fixture containing a realistic member record (name, DOB,
  diagnosis), (3) `Determination` records missing `decidedBy`. Trace the
  transcript, match each finding to its dimension, then 3 check questions
  (with answers) on which checkpoint should have caught each one.
- **Path B — Build It with AI:** unit of work = "audit and hygiene guardrails"
  on `prior-auth-api`. Both engine variants produce the same two artifacts:
  1. A **Responsible AI rules** section appended to the steering file
     (CLAUDE.md / AGENTS.md — same content, per the one-pattern-many-names
     framing): never modify `AUTO_APPROVE_THRESHOLD` without recorded human
     approval; fixtures synthetic-only, no realistic member data; every
     `Determination` must carry `matchScore`, `criteriaVersion`, `decidedBy`.
  2. A plan-first bolt: extend the `Determination` type with the three
     provenance fields and add Jest tests asserting (a) sub-threshold requests
     never auto-approve and (b) every determination carries provenance.
  Claude Code variant: plan mode for step 2, checkpoint, then build; Codex CLI
  variant: suggest-mode plan, review, then apply. Engine parity: identical
  steering-file section, identical type change, identical test assertions.

## Recap bullets

1. Responsible AI in AI-DLC is not a new stage — each dimension attaches to a
   checkpoint the lifecycle already runs, which is why the compliance answer is
   fast and true.
2. The auto-approval threshold is a clinical-policy decision: engines may read
   it, only named humans may move it, and the nurse review queue is the
   fairness backstop beneath it.
3. Context leaves the building: decisions and schemas go in the chain; member
   data never enters a prompt, a fixture, or a steering file.
4. Explainability is schema: `matchScore`, `criteriaVersion`, `decidedBy` on
   every Determination; provenance for code is the chain plus
   understand-every-line.
5. The engine builds; the names on the checkpoint answer for the build. Course
   complete — go run a bolt, responsibly.
