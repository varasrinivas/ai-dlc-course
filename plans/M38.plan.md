## Concept outline

1. **The stage chain, and what always runs** (`<h2>`)
   - Three Ideation stages close out first: Market Research (already in progress, so it can't be
     skipped), Scope Definition (writes `intent-backlog.md` with proto-units) and Approval Handoff
     (gate: Approve / Request Changes / Reject Initiative, plus the phase check). One paragraph, no
     more; fig 38.1 carries them.
   - Inception for this intent: 2.1 → 2.3 → 2.4 → 2.6 → 2.7 → 2.8 → 2.9, seven gates.
     `ALWAYS` marks the stages a scope can't drop: requirements, units, delivery planning.
   - 2.1 Reverse Engineering writes nine files to `aidlc/spaces/default/codekb/<repo>/`. That is
     M12's semantic map, now with a freshness check: `CURRENT` offers reuse, `STALE` forces a rescan,
     and the person picks. Excerpt one real file (`business-overview.md` or
     `code-quality-assessment.md`, whichever names the 0.85 path).
2. **Questions files: Mob Elaboration is still the room** (`<h2>`)
   - Each stage writes `<stage>-questions.md`: options A–E plus `X. Other`, blank `[Answer]:` tags,
     about 5–8 per stage at Standard depth. The mode is chosen once (Guide me / I'll edit the file /
     Chat) and reused; M36 chose "edit the file".
   - In edit-file mode the agent must not read the file until the person sends `done`. The rules:
     "never choose for them", and "the tool refuses a self-selected answer". Then a summary
     confirmation (Looks correct / Request changes) and the gate.
   - M06's ritual maps onto this directly. The team fills the file together; the engine's
     follow-ups take the place of the facilitator's clarifying loop. Show one real answered
     question from 2.3 and how it lands in `requirements.md` as an FR/NFR id.
3. **Two kinds of mob** (`<h2>`)
   - User Stories is the graph's only `mob` stage. With collaborators on: Round 0 the product agent
     drafts; Round 1 design, developer and QA agents contribute "mutually blind" into
     `contributions/<agent>.md`; triage sends knowledge disputes to Round 2 and judgment calls to a
     person. The engine's own line: "The human is a mob participant, not a post-hoc approver."
   - `feature` ships `collaborators: off`. The team turns it on in chat ("bring the specialists
     in") for this stage only. Show which real contribution changed a story, and which judgment call
     came to the team.
   - The agent mob widens the draft. The people still decide. Neither one replaces M06's room.
4. **Units, contracts and the bolt plan** (`<h2>`)
   - 2.7 writes `unit-of-work.md` (U1…, kind service/spec/ui/…) and a yaml DAG in
     `unit-of-work-dependency.md`. The stage "MUST NOT recommend an implementation order"; the DAG
     carries the dependencies. 2.8 runs because there is more than one unit (or an external API), and
     writes `contract-summary.md`.
   - 2.9 writes `bolt-plan.md`: units per bolt, walking-skeleton marker, Definition of Done,
     confidence hypothesis, expected demo. It also asks the person to approve a verification command.
   - The engine orders Construction from the DAG, not from `bolt-plan.md`: "Reordering only
     `bolt-plan.md` does not change the Unit the engine builds first." The bolt plan is for people
     (M33's board); the DAG is for the engine. M39 starts here.
   - (Word budget: sections 1 and 4 are at risk. The stage list goes into fig 38.1, the DAG into
     fig 38.2.)

## Recap bullets

- Inception on the engine is a chain of stages, each with a questions file and a gate. A scope can't
  drop requirements, units or delivery planning.
- Reverse Engineering writes nine `codekb/` files per repo and checks them for freshness next time.
- The engine asks; the team answers in the file together, and the engine refuses to choose for them.
  That is Mob Elaboration, kept.
- The agent mob in User Stories widens the draft; judgment calls still come to a person.
- The engine builds in DAG order. `bolt-plan.md` is the team's view of the same work.
