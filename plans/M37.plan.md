## Concept outline

1. **Scope picks the stages; depth picks the detail** (`<h2>`)
   - 11 stock scopes, each a file in `.claude/scopes/`, set which of the 33 stages EXECUTE and
     which SKIP. The real table: `bugfix` 9/33 at Minimal, `feature` 33/33 at Standard,
     `enterprise` 33/33 at Comprehensive. `feature` and `enterprise` run the same stages and differ
     in depth and Guard Policy.
   - Depth (Minimal / Standard / Comprehensive) changes how much each stage writes, not whether it
     runs. A test strategy can override depth for testing alone (`workshop`).
   - A scope also carries six settings the person can flip per intent: sensors, learnings,
     summary confirmation, plan approval, collaborators, review (`adversarial` / `advisory` /
     `none`). `express` turns plan approval off; only the person turns it off on any other scope.
2. **The composer proposes; a person approves** (`<h2>`)
   - `/aidlc compose "<task>"` runs a read-only scan, scores five things (intent ambiguity,
     structural uncertainty, verification entropy, risk, unresolved assumptions) and proposes a
     grid with a reason for every SKIP. A validator checks the grid. If it matches a stock scope the
     plan is "matched"; otherwise it's "custom", built on a base scope.
   - The gate: Approve / Edit the plan / Reject. A custom plan adds "Approve and save as scope",
     which runs `aidlc engine scope save --name <name>` so the shape can be reused. Saved scopes are
     matched by keywords the person grants, never guessed.
   - On a running intent the composer is narrower. It may only skip or add stages that haven't
     started; scope, depth and every finished stage stay as they are, and the change lands as a
     `RECOMPOSED` audit event. Named stage changes ("skip market research") apply at once, with
     the undo stated.
   - The engine's own line: "The composer proposes; the human decides; the deterministic validator
     guards." It is M10's invariant, now in AWS's words.
3. **Guard Policy: who can lower the checks** (`<h2>`)
   - Three modes. `strict`: a changed input reopens approval and no fences are lowered. `off` (the
     default for ten of eleven scopes, including `feature`): changed inputs are "recorded and
     announced, the run continues", and plan approval, review freeze, state transition and reviewer
     read scope are lowered for undirected work. Human presence stays up in every mode. `relaxed`
     sits between them (exact behaviour to quote from the capture run).
   - The engine's guard rule: when a person asks in their own words to turn a check off, the agent
     does it in the same turn and must "never refuse". A single chat line can lower the checks on
     the threshold path. That's by design, not a bug.
   - The lock: a `strict` line under `## Guard Policy` in `memory/project.md` "holds for every
     intent, whatever one person asks in chat". The setter then refuses with one line naming the
     file. This is M17's hook-enforced lock: a rule a team agrees once, which no single prompt can
     undo. `/aidlc --status` shows the policy and each fence with where its value came from.
   - (Word budget: this section is at most risk. The check table goes into fig 37.2, not prose.)
