## Concept outline

1. **What the installer writes, and where** (`<h2>`)
   - Two installs, two scopes. The machine install is per user: `%LOCALAPPDATA%\aidlc\`, holding
     `bin\aidlc.cmd` and `versions\2.11.0\`, plus a user PATH entry. It changes no project. The
     project install is `aidlc config --harness <name>`, run in the folder you want the engine in.
   - What config wrote in the reference hub (from the real run): an engine directory per harness
     (`.claude/`, `.codex/`, plus `.agents/skills/` for Codex), holding agents, hooks, the 33 stage
     files, 11 scope files and the tools. Also the `aidlc/spaces/default/memory/` tree, a root
     `AGENTS.md` block, and managed `.gitignore` blocks. About 700 files in all; you edit none of the
     engine files.
   - Initialization 0.1–0.3 runs later, automatically and without a gate, when the first intent is
     created (M36). Config only builds the shell.
2. **One hub, two engines, repos beside it** (`<h2>`)
   - The hub is its own git repo. `repos.json` declares the code repos, and
     `aidlc system workspace-sync` clones them in as siblings. The hub `.gitignore` keeps their code
     out of the hub's commits: the hub commits the record, and each repo commits its code.
   - Each engine reads the method by its own route:
     - Claude Code: `.claude/CLAUDE.md` → `@.claude/rules/aidlc.md` → `@` imports of each `memory/*.md`.
       These are ambient, loaded before the first prompt.
     - Codex: the root `AGENTS.md`, plus `developer_instructions` in `.codex/config.toml`. The
       orchestrator injects the memory paths on demand when `$aidlc` runs.
     - Same method, different enforcement: the same lesson as the M19 note on `docs/decisions.md`.
   - Two first-run steps can't be scripted: Codex hook trust (`/hooks`, `t`, Esc), and restarting
     Claude Code after config.
   - Where the hub lives: never inside a folder whose parents hold a `CLAUDE.md` you don't want
     loaded. Claude Code walks up the tree. (This is why the course's hub sits outside the kit.)
3. **A file only becomes memory when something loads it** (`<h2>`)
   - The course's own line, from the practice repos' `CLAUDE.md`. At the hub it bites: the engine runs
     at the hub root and loads `aidlc/…/memory/`. It does not load `prior-auth-api/AGENTS.md`, where
     the threshold, the eligibility rule and the no-clinical-content rule live.
   - Worse, a search from the hub doesn't find them either. The hub's managed `.gitignore` lists the
     sibling repos, and Claude Code's Grep respects `.gitignore`. In the real "before" probe, a
     workspace-wide search for `AUTO_APPROVE_THRESHOLD` returned "No matches", and the engine
     concluded the setting "doesn't exist in this project".
   - The fix is three short blocks in `memory/project.md`, under its existing `## Way of Working`,
     `## Forbidden` and `## Mandated` headings. The Way of Working line says "each repo's AGENTS.md
     governs its own code; read it before changing that repo". These are rules, not a copy of the
     whole file. In the real "after" probe, the engine cited `project.md`, then followed that pointer
     into `prior-auth-api/AGENTS.md` and D-001 before refusing.
   - Not every repo rule belongs in `project.md`. The engine flagged that tests-first conflicts with
     `org.md`'s test-after default, which says a stricter testing method belongs in `team.md` under
     Testing Posture. Rules that describe today's known gaps stay out too, because they would block
     the work that fixes them.
   - Hand edits load, but they leave no audit trail. The engine's own route is stage 2.2 Practices
     Discovery or its learnings step, which promote rules through an affirmation gate (M38). The lab
     edits by hand, on purpose, so the first intent starts with the guardrails in place. Say plainly
     that this trades the trail for an earlier start.
4. **Doctor is the setup's own checklist** (`<h2>`)
   - The real before/after run:
     - Before config: 4 problems, each naming the command that fixes it.
     - After config: 0 problems and 3 warnings (update cache absent; hooks not run yet; uncommitted
       `aidlc/` records). All three are expected on a fresh hub.
   - The native `aidlc doctor` checks the Claude Code project here. The Codex setup is checked from
     inside Codex with `$aidlc --doctor`, after hook trust.
   - The version stamp: Track 8 states the engine version it was verified against, because v2
     ships often. Re-run doctor after every upgrade.

## Recap bullets

- The engine installs per user; `aidlc config` builds a project shell in the folder you run it
  in. Everything under `.claude/`, `.codex/` and `.agents/` is the engine's; `aidlc/` is your
  record, and you commit it.
- One hub, sibling repos, both engines: `repos.json` and `workspace-sync` set it up, and each repo
  keeps its own code and git history.
- A clean doctor proves the plumbing, not the method. The engine loads `aidlc/…/memory/`, so your
  guardrails go there before the first intent.
- Claude Code loads that memory on every turn; Codex loads it when `$aidlc` runs. Same method,
  different enforcement.
